# Native Packaging and Cross-Platform Architecture

TableSpark 2.0.12 now includes a Tauri 2 native shell in addition to the existing web/PWA delivery path. The earlier decision to defer native packaging has been superseded by the explicit cross-platform requirement.

The product still keeps one React/TypeScript learning application and one local-data model. Tauri provides the platform shell rather than duplicating the multiplication, practice, mastery, localization, persistence, accessibility, or worksheet logic in separate native applications.

## Supported delivery targets

| Target | Delivery model | Repository command |
| --- | --- | --- |
| Web | Static Vite build | `npm run build` |
| PWA | Static Vite build + service worker | `npm run build` |
| Windows | Tauri desktop application / installer | `npm run native:build` on Windows |
| macOS | Tauri desktop application / bundle | `npm run native:build` on macOS |
| Linux | Tauri desktop application / package | `npm run native:build` on Linux |
| Android | Tauri Android project producing APK/AAB packages | `npm run android:build` |
| iOS/iPadOS | Tauri iOS project producing Apple application packages | `npm run ios:build` on macOS |

The target platform decides the native webview and packaging toolchain. The React application remains shared.

## Why Tauri 2

Tauri 2 was selected because it supports the existing Vite frontend and can target Windows, macOS, Linux, Android, and iOS from one application project. It also allows the native permission surface to remain small because TableSpark does not need a general-purpose shell, filesystem access, network backend, or privileged learner-data API.

The native implementation is intentionally thin:

```text
React / TypeScript product
        ↓
Vite production assets
        ↓
Tauri 2 shell
        ↓
platform system webview
        ↓
Windows / macOS / Linux / Android / iOS
```

## Repository structure

Native source lives under `src-tauri/`:

```text
src-tauri/
├── Cargo.toml
├── build.rs
├── capabilities/
│   └── default.json
├── src/
│   ├── lib.rs
│   └── main.rs
├── tauri.conf.json
├── tauri.android.conf.json
└── tauri.ios.conf.json
```

Generated Android/iOS IDE projects and Rust build output are not committed:

```text
src-tauri/gen/
src-tauri/target/
```

They are reproducibly regenerated by the Tauri CLI. This keeps large machine-generated native projects out of the maintained source tree while retaining explicit configuration and commands in version control.

## Shared versioning

Product version remains `2.0.12`.

Version sources are synchronized as follows:

- `package.json` is the primary product semantic version;
- `src-tauri/tauri.conf.json` reads its version from `../package.json`;
- `src-tauri/Cargo.toml` carries the same package version and is checked by the native configuration gate;
- English/Hindi visible About/Settings copy is tested against `package.json`;
- Android version code is derived by Tauri from the semantic version unless explicitly overridden;
- iOS/macOS short version comes from the Tauri product version.

`npm run native:config:check` fails when maintained native configuration drifts from these invariants.

## Web versus native runtime behavior

The Vite build receives Tauri hook environment metadata when it is built by the native toolchain.

TableSpark exposes build-time constants:

- `__TABLESPARK_NATIVE__`
- `__TABLESPARK_PLATFORM__`

The runtime abstraction in `src/platform/runtime.ts` uses them to distinguish ordinary browser/PWA builds from packaged applications.

### Service worker

Browser/PWA builds register the production service worker normally.

Native Tauri builds do **not** register the PWA service worker because the packaged application already owns its local application assets and should not run a second browser-style update/cache lifecycle on top of the native package lifecycle.

### External links

Browser builds continue to use normal anchors.

Native builds use the Tauri opener plugin so GitHub, support, funding, and `mailto:` destinations are handed to the operating system instead of navigating the TableSpark webview away from the application.

The native capability does not permit arbitrary shell execution or arbitrary file opening. URL permission is scoped to the exact maintained TableSpark contact/project destinations.

## Local learner data across platforms

TableSpark remains local-first.

The learner-state schema and validation rules are unchanged by the native wrapper:

```text
schemaVersion: 2
storage key: tablespark.state.v1
```

Each browser profile or installed native application has its own platform-managed webview storage. Installing TableSpark as a native application does not silently import a browser/PWA profile from another origin or device.

To move learner data between installations, use validated JSON backup export/import. This explicit transfer boundary is safer than attempting to discover or copy another platform's private webview storage automatically.

## Desktop development

After Node/npm, Rust, and platform-native Tauri prerequisites are installed:

```bash
npm install
npm run native:info
npm run native:dev
```

Compile without generating installers:

```bash
npm run native:build:ci
```

Create the platform bundle/installers supported by the current host:

```bash
npm run native:build
```

A desktop host builds its own platform. Cross-compiling every desktop installer from one host is not assumed.

## Android development

Required host tooling includes Android Studio/SDK tools, Java, Android NDK, and the Android Rust targets.

Generate the Android project:

```bash
npm run android:init
```

Run a development application:

```bash
npm run android:dev
```

Build packages:

```bash
npm run android:build
```

For a local unsigned/debug APK verification path:

```bash
npm run android:build:debug
```

The package identifier derives from:

```text
in.sanskar.tablespark
```

Debug builds add `.debug` so they can be distinguished from a release installation.

Minimum Android API level is 24.

## iOS/iPadOS development

iOS builds require macOS with full Xcode tooling.

Generate the iOS project:

```bash
npm run ios:init
```

Run in development:

```bash
npm run ios:dev
```

Build a release package after signing is configured:

```bash
npm run ios:build
```

For simulator-oriented validation:

```bash
npm run ios:build:simulator
```

The configured minimum iOS version is 14.0.

## Native CI

`.github/workflows/native.yml` provides repository-level verification separate from the web CI.

Current jobs:

- compile the desktop application without installers on Ubuntu/Linux;
- compile the desktop application without installers on Windows;
- compile the desktop application without installers on macOS;
- run Rust formatting/type checks;
- verify Android project generation on Ubuntu;
- verify iOS project generation on macOS.

Android/iOS store signing is intentionally not performed in pull-request CI because signing credentials must not be exposed to untrusted PR code.

## Signing and distribution security

Native store/distribution packages introduce release credentials that the PWA did not require.

Never commit:

- Android keystores;
- Android `keystore.properties`;
- Apple `.p8` API keys;
- `.p12` signing certificates;
- provisioning profiles;
- signing passwords or private keys.

The root `.gitignore` blocks common signing artifacts as defense in depth. Real signing material belongs in a protected release-secret system or a secure local signing environment.

Before publishing native packages, document and verify:

1. package/bundle identifier ownership;
2. signing-key ownership and backup;
3. store/developer-account ownership;
4. signed artifact identity;
5. version/build-number policy;
6. platform privacy declarations;
7. installation and upgrade behavior;
8. rollback/replacement process.

## Platform-specific limitations

Cross-platform support does not mean every operating-system facility behaves identically.

Examples:

- system print dialogs are supplied by the active browser/webview/platform and need real-device verification;
- speech synthesis voices and availability differ by system webview;
- keyboard shortcuts may be intercepted by the OS;
- mobile webviews use mobile platform interaction conventions rather than desktop window behavior;
- signed store distribution requires platform-owner credentials;
- application data stays inside each installation's platform storage sandbox.

The shared domain/data invariants must remain identical even when host capabilities differ.

## Architecture rule for future features

A new product feature should remain in the shared TypeScript/domain layer unless it genuinely requires a native API.

If native access is required:

1. add only the narrow official/plugin capability needed;
2. scope permissions to the minimum resources/URLs/operations;
3. keep a browser fallback when the product requirement allows it;
4. test web and native behavior separately;
5. document privacy/security consequences;
6. never expose general shell/process/filesystem access merely for convenience.

This keeps TableSpark cross-platform without turning the native shell into a second application architecture.
